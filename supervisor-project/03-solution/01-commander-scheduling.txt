1. Overview

This solution document describes how Commander decides when each CAMT report runs and what time
period it covers. Which recipient and customer agreement scope a run actually applies to is
resolved downstream, once scheduling hands off — see 1.1 for that boundary, and
02-commander-message-production-pipeline.txt and 03-commander-data-retrieval.txt for how the
resolution itself happens.

1.1 Conceptual Overview

Scheduling has exactly one job: on a timetable, wake up and say "produce this report type,
covering this time window." It then hands that instruction off to the Message Production
Pipeline and steps away. It does not build the report, does not look up a configuration's own
metadata or resolve the agreement scope beneath it (which cascades down to payment types,
accounts, and aliases), and does not track whether the run ultimately succeeded — those are
separate concerns, owned by the Message Production Pipeline and the Data Retrieval layer
respectively (see 02-commander-message-production-pipeline.txt and
03-commander-data-retrieval.txt).

Every firing resolves to a small, fixed set of facts — report type, frequency, the moment it
was scheduled for (the scheduled fire time), and the reporting window's start and end — handed
to the Message Production Pipeline as one package. The reporting window itself is always computed
using one of three shapes: Rolling (a fixed look-back ending at the fire time), Boundary
(the stretch since the previous checkpoint today, anchored to midnight), or Calendar-day (the
whole previous calendar day, delivered the next morning). Both of these are introduced only
briefly here, because the rest of this document refers to them by name; the full detail for
both lives in 1.6 (Logical View - Architecture Scope).

1.2 Scope and Acceptance Criteria

In scope:

  - How often (the cadence) each report type runs (Rolling, Boundary, and Calendar-day frequencies).
  - The reporting-window computation rules for each cadence, including daylight-saving
    behaviour.
  - Connecting to Quartz, the clustered job scheduler this application uses to wake up on a
    timetable.
  - The declarative format used to describe a schedule in the application's own configuration — report
    types, frequency, days, and either an interval or an explicit list of boundary times (see
    1.4, decision 6) — from which the application builds the actual cron trigger(s).
  - The admin actions available: Run now, Backfill, Pause, Resume, and Status.

Out of scope:

  - Producing the report messages themselves, and resolving each configuration's own metadata
    and the agreement scope beneath it (payment types, accounts, and aliases) — owned by the
    Message Production Pipeline and the Data Retrieval layer.
  - A schedule-management UI, or any runtime editing of the timetables themselves — schedule
    shape (report types, frequency, days, boundaries) is deploy-time configuration, changed by
    redeploy, not a live edit.
  - Holiday calendars — the business day is Monday to Friday, with no holiday exceptions.

Acceptance criteria — to be verified once this is implemented, under a real clustered
deployment:

Normal operation:

  - Every configured schedule fires at its correct time(s) and produces a window that matches
    the shape rules in 1.6 — verified with worked examples for at least one Rolling, one
    Boundary, and one Calendar-day frequency.
  - The five facts handed to the Message Production Pipeline (1.1, 1.6) are correct for every
    firing: report type, frequency, scheduled time, window start, and window end.
  - Two overlapping firings for the same report type and frequency both run to completion and
    both publish, with neither blocking the other (decision 8 in 1.4).
  - Each admin action — Run now, Backfill, Pause, Resume, Status — produces the expected
    result under normal conditions: Run now fires immediately with the correct window;
    Backfill recovers exactly the slot(s) requested; Pause and Resume affect only the targeted
    schedule; Status accurately reports paused/active state plus last and next fire time.
  - After a redeploy with no schedule changes, startup reconciliation leaves every valid
    trigger intact and every schedule continues firing exactly as before.

Recovery and failure handling:

  - A genuinely missed firing is skipped cleanly under the do-nothing misfire policy (a
    missed slot is never automatically caught up — see decision 2 in 1.4 and 1.7.B), and the
    next scheduled fire is unaffected.
  - The same holds for a schedule resumed after being paused across one or more of its fire
    times.
  - When a pod is killed and the scheduler's own clustering re-fires the affected job: if no
    tracking record existed yet for that firing, one is created and processing proceeds
    normally; if one already existed, the re-fired execution recognizes it and exits cleanly —
    no duplicate record, and no double-published report, either way.

1.3 Information Relevant for Prioritization

1.4 Architectural Decisions

  1. Clustered scheduler with job recovery enabled. The scheduler runs in clustered mode, so
     exactly one pod across the deployment picks up any given firing. Job recovery is enabled
     on every scheduled job so that a pod dying before it manages to create the pipeline's
     tracking record does not silently lose that firing — this closes a gap the pipeline's own
     recovery mechanism cannot see by itself, since it only ever examines tracking records that
     already exist.

  2. Do-nothing misfire policy; recovery only via explicit backfill. A firing that is missed —
     whether from an outage or a deliberate pause — is not automatically caught up. The
     timetable simply resumes at its next natural time. Recovering a missed slot is always a
     deliberate operator action (backfill), available for any missed slot, sub-daily or
     end-of-day alike, and is idempotent to re-issue. A database outage is the single most
     likely real-world cause of "the whole cluster is down" (decision 1, and the assumption in
     1.5 about Quartz's dependency on the database) — it is handled the same way as any other
     outage: nothing is caught up automatically, and recovering whichever slots actually matter
     is a deliberate backfill once the database is healthy again, the same as after any other
     outage.

  3. Every-2-hour and every-4-hour frequencies re-classified as Boundary, anchored to
     midnight. This is a deliberate departure from the legacy system (the system Commander is
     replacing), which treats these two as a rolling look-back and leaves 00:00-01:00
     unreported each day. Anchoring to midnight closes that gap and brings these two
     frequencies in line with the "N times a day" boundary frequencies, which already cover
     from midnight. This is worth flagging explicitly during cutover parity comparisons
     against the legacy system.

  4. Fixed, explicit daylight-saving rules. Clocks move forward an hour each spring (one hour
     is skipped that day) and move back an hour each autumn (one hour happens twice that day).
     Scheduling handles both cases the same way: a report due to fire during the skipped
     spring hour fires at the next real time instead of not firing at all; a report due to
     fire during the repeated autumn hour fires only the first time that hour happens, not the
     second time. This rule must be built as our own code — deliberately written and tested.

  5. One job implementation, parameterized per schedule. The differences between schedules —
     report type, frequency, and the window specification — live in each job's own
     configuration data, not in separate job subclasses. This keeps the scheduling logic in one
     place regardless of how many report type / frequency combinations exist.

  6. Cron expressions are generated from declarative configuration, never hand-authored. An
     operator describes a schedule in plain terms — report types, frequency, days, and either
     an interval or an explicit list of boundary times — and the application derives the
     underlying "cron" timing expression from that. This matters because the same boundary
     list also drives the window calculation; if the timing rule were hand-written separately, the two could silently drift apart from each other.

  7. Scheduling's responsibility ends at the handoff. A firing creates a tracking record as
     its first durable action, checks a feature flag for that report type, and then hands off
     exactly five facts to the pipeline. It does not build reports, does not look up a
     configuration's metadata or its agreement scope, and does not track whether the
     handed-off work eventually succeeds.

  8. Concurrent runs for the same report type and frequency are allowed by design. If one
     window's run is still in progress when the next window's run fires, both are allowed to
     run and publish at the same time — a slow run must never hold back the next window's
     report. There is no mutual-exclusion lock preventing this.

  9. One uniform set of admin actions, addressed by (report type, frequency). Run now, Backfill,
     Pause, Resume, and Status all address a schedule the same way regardless of its window
     shape, so operators have one consistent mental model for controlling any schedule.

1.5 Assumptions and Pre-Requisites

  - The business timezone is fixed at Europe/Stockholm for all window computation; it is
    converted to absolute time only for the outgoing message.
  - The business day is Monday to Friday. There is no holiday calendar — a weekday holiday
    still runs its scheduled firings and produces a (possibly near-empty) report.
  - The deployment runs as multiple pods in a clustered environment. Scheduling's choice of a
    clustered, job-store-backed scheduler to guarantee exactly one pod picks up each firing
    (decision 1 in 1.4) depends on that being true.
  - A feature-flag mechanism (a simple on/off switch per report type) exists and is
    addressable per report type, so scheduling can gate a firing before handing work to the
    pipeline.
  - Quartz's own job store — the thing that lets it know what is due and coordinate which pod
    picks up a firing — lives in the same shared database as the rest of the deployment. If
    that database is unreachable, Quartz cannot determine what's due or coordinate anything, so
    scheduling stops entirely: nothing fires at all until the database is reachable again. This
    is treated as an inherent consequence, not something scheduling can resilience around —
    but it does mean a database outage needs its own infrastructure-level alerting, since
    scheduling's own alerting depends on scheduling being able to run in the first place. See
    db-mq-failure-analysis.md (01-requirements) for the fuller analysis.

1.6 Logical View - Architecture Scope

Scheduling is made up of the following logical components:

  - Trigger loader / generator — reads the deploy-time schedule configuration, expands any
    entry that lists several report types into one independent schedule per report type,
    generates the underlying cron timing expression(s) from each schedule's interval or
    boundary-list specification, and builds and registers the resulting job and trigger definitions
    with the clustered scheduler at startup.

  - Startup reconciliation — also at startup, before the scheduler begins running, removes any
    triggers left over from a prior configuration so that nothing fires against a stale
    schedule.

  - Job implementation — one job class, invoked whenever any of its registered triggers fires.
    The differences between schedules — report type, frequency, and the window specification —
    live in each job's own configuration data rather than in a separate subclass per schedule
    (decision 5 in 1.4), so the same implementation serves every report type and frequency.
    This is the component that carries out the sequence in 1.7: resolving the window, creating
    the tracking record, checking the feature flag, and handing off to the pipeline.

  - Window function — a straightforward pure calculation that resolves a scheduled fire time to a
    (window start, window end) pair. Every report frequency falls into one of three window
    shapes — this is the whole mental model for how a reporting window is computed:

      - Rolling — "the last N minutes." The window is a fixed look-back ending at the fire
        time. A run every 30 minutes at 13:00 covers 12:30-13:00; at 13:30 it covers
        13:00-13:30. Used for the highest-frequency intraday reports.

      - Boundary — "since the previous checkpoint today." The day has a fixed set of clock
        times; each run covers the stretch from the previous checkpoint to this one, with
        midnight as an implicit first checkpoint. Used for the "N times a day" notification
        reports, and also for the every-2-hour / every-4-hour intraday reports, anchored to
        midnight the same way.

      - Calendar-day — "all of yesterday." The window is the entire previous calendar day,
        midnight to midnight; the run simply happens the next morning to deliver it. Used for
        the end-of-day statements.

    All window math happens in one configured business timezone, Europe/Stockholm, and is
    then converted to absolute time for the outgoing message. The daylight-saving resolution
    rules layered on top of this are covered as decision 4 in 1.4.

  - Clustered scheduler layer — fires triggers such that exactly one pod across the deployment
    handles any given firing, with job recovery enabled so a pod that dies before completing a
    firing's first durable step does not silently lose that firing.

  - Admin control surface — an authenticated, admin-only set of actions for Run now, Backfill,
    Pause, Resume, and Status, addressed by (report type, frequency).

Handoff boundary: Scheduling hands off exactly five facts to the Message Production Pipeline
(02-commander-message-production-pipeline.txt), as one package:

  - report type
  - frequency
  - the moment it was scheduled for
  - window start
  - window end

The tracking record for the firing is created as the very first durable step, before this
handoff happens — the full step-by-step sequence is in 1.7. From there, the pipeline resolves
the matching configurations and builds and publishes the messages; it in turn depends on the
Data Retrieval layer (03-commander-data-retrieval.txt) to resolve each configuration's
agreement scope — the payment types, accounts, and aliases beneath it. Scheduling itself has no
visibility into whether a handed-off firing eventually succeeds — that is tracked entirely
downstream.

Visual reference: scheduling-flow.drawio (draw.io / diagrams.net) — page 1 the three trigger
sources, page 2 the scheduled job lifecycle (including the misfire / backfill branch), page 3
the three window shapes on a timeline, page 4 clustered scheduling across pods.

1.7 Workflow / Process Flow

A. When a schedule fires

  1. The timetable is due. Because the scheduler runs in clustered mode, exactly one pod
     across the whole deployment picks up the firing — a property of the clustering
     technology itself, not something the application has to coordinate.

  2. That pod resolves the window using the shape rules from 1.6, from the time the firing
     was scheduled for — never the wall-clock time it happened to wake up at. For a normal
     firing these are the same instant; the distinction matters for a manual backfill or a
     recovered run, where the report must cover the period it was meant to, not whenever it
     actually ran.

  3. It creates one tracking record (a "Run") as its first durable action — precisely so that
     anything that goes wrong afterward leaves a trace recovery can act on.

  4. It checks a feature flag for that report type. If the flag is off, the Run is marked
     skipped right there and nothing is handed to the pipeline — no configurations are
     resolved, nothing is built. If the flag is on, it hands the pipeline the five facts from
     1.6. The pipeline takes it from there — finding the matching configurations, resolving
     their data, building and publishing the messages.

  A skipped Run still occupies that slot — that is final, not something to backfill. If that
  window's report is still wanted, that is an on-demand request instead, not a retry.

  Daylight saving: a fire time that falls in the skipped spring-forward stretch shifts forward
  to the next real moment; one that falls in the repeated autumn stretch fires once, at its
  first occurrence. A rolling frequency caught in that stretch ends up with a window whose
  start and end resolve to the same instant — an empty report, not a wrong one.

B. When a firing is missed

  A firing can go missing for more reasons than an outage alone — the whole system being down
  is the most common cause (most often because the shared database is unreachable, which stops
  scheduling entirely, see 1.5), but it also happens if an operator has deliberately paused that
  schedule (for example, to protect production during an environment issue, or because they've
  been informed of a database or message-queue problem and are riding it out on purpose).
  Whatever the cause, it is handled the same way: the automatic policy is to do nothing. The
  missed slot is skipped entirely; the timetable simply resumes at its next natural time and
  produces that window normally. There is no automatic catch-up, ever, for any report.

  Recovering a missed slot is always a deliberate action, available for any missed slot,
  sub-daily or end-of-day alike. An operator (or a small admin endpoint) fires the schedule
  again, passing the missed slot's time, and it produces exactly the window that firing would
  have produced on time. This is idempotent (safe to repeat) — re-issuing a backfill for a slot that
  already ran simply does nothing the second time.

  This is also the intended shape of a deliberate pause: pause the schedule to ride out the
  issue, fix it, resume for firings going forward, then — once it is agreed which slots
  actually matter — backfill exactly those. This is the operator's main tool during a known
  database issue too: pause the affected schedules once informed there's a problem, resume once
  the database is confirmed healthy, and backfill afterward if any of the missed windows still
  matter (see db-mq-failure-analysis.md, 01-requirements, for the fuller reasoning).

C. Reliability behaviours worth knowing

  - Overlapping runs are allowed on purpose. If one window's run is still going when the next
    window's run fires, both run at the same time and both publish — a slow run must never
    hold back the next window's report.

  - A repeated firing for the same slot is a harmless no-op, not an error. Whichever firing
    gets there first creates the tracking record; any other firing for the exact same slot
    finds it already exists and exits without doing any further work. Nothing is built or
    published twice, and it is not treated as a failure.

  - A crashed pod's work is always recovered — which mechanism handles it just depends on
    timing. If the pod dies before it could even create the tracking record, the scheduler's
    own clustering re-fires that firing on a live pod, and it starts fresh. If the pod dies
    after the tracking record was created but before the run finished, the pipeline's own
    recovery mechanism notices and resumes from where the pod stopped. These two never clash —
    a re-fired attempt always tries to create the tracking record first, and if it already
    exists, it just stops, the same no-op as a repeated firing above.

  - Redeploys clean up after themselves. If a previous configuration's timetables are still
    registered, the application removes them at startup, before the scheduler starts running
    — so nothing fires against a stale schedule.
